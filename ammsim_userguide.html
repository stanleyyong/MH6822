AMM Simulator Documentation

A single-file Uniswap V3 simulator with concentrated liquidity, a public mempool, adversarial searchers, the mitigations they face, and a coupled lending pool that makes oracle attacks actually profitable.

Pools 4 (5bp / 30bp / 1bp)
Agents 33 across 8 types
Builders 4 competing per block
Format Single HTML file, no deps

This is a Uniswap V3 simulator that runs in your browser. It has four pools with seeded liquidity, 33 agents (passive LPs, retail traders, five fund subtypes, a stat-arb agent, and toggleable MEV searchers), a public mempool, four block-builders that compete each block, and a coupled lending pool whose WETH oracle reads from the AMM.

You can switch between MEV strategies, change the lending oracle from spot to TWAP-30, load a mainnet TVL snapshot, fast-forward by hours, and read forensic metrics in real time. CSV exports of every swap and event are one click away.

The simulator is meant for building intuition about how AMMs behave under different flow regimes and adversarial conditions. It's not calibrated to any specific historical period and doesn't replay on-chain events. If you want that, the CSV schemas match what you'd expect from pandas after a Dune query.

Switching modes mid-run is the most useful thing you can do. A clean way to start: run in sandwich mode for 6 hours of sim time, note the searcher P&L, then switch to protected and run another 6 hours. The dollar gap between the two is what private orderflow is worth to a trader on that flow profile.

Open the file, hit START, switch modes. Below is a step-by-step that touches the most useful controls in roughly the order you'd want to learn them.

Five minutes to first MEV

  1. Open amm.html in a browser

    The page loads with all four pools seeded, agents created but idle, sim paused. The top bar shows the active pool's price, TVL, cumulative volume, and a UTC clock that drives diurnal flow intensity. The default time is 13:00 UTC, which is the peak of the US/EU overlap window.

  2. Hit ▶ START

    Retail and fund txs start flowing into the public mempool. The mempool panel shows pending txs ordered by gas tip. Every 12 seconds a block closes — four builders each construct a candidate block, the proposer picks the one with the highest value, and that block is what executes.

  3. Click 🥪 Sandwich

    Two sandwich-searcher agents (SAND1, SAND2) activate. They scan the mempool every sim-tick for victims, size their front-run to fit inside the victim's slippage tolerance, and submit paired front/back txs. Watch the forensics panel — Attempts and Profitable counters update in real time. Success rate stabilizes around 60% on the 5bp pool against whale victims.

  4. Switch to 🛡 MEV-Protected RPC

    Sandwich attempts drop to zero. In the Builder Competition section of forensics, you'll see Protect-Builder go from never winning to winning every block — because protected txs are invisible to the other builders, only Protect-Builder can include them, so its blocks are the only ones with positive value.

  5. Switch to 🔮 Oracle Attack

    Now ORC1 is active. Oracle attacks fire stochastically about once every 200 blocks. Use +6h to fast-forward — in a 6-hour skip you'll usually see one or two attacks. Each one: ORC1 sells $50M of WETH on USDC/WETH, holds for 8 blocks while the lending pool reads its WETH oracle from the depressed price, liquidates 3–5 borrowers at the 8% bonus, then unwinds the AMM position.

  6. Toggle the lending oracle to TWAP-30

    The toggle is on the right side of the strategy bar. Run the same oracle attack experiment with TWAP active — ORC1's profit drops by about 80%. The attack still fires (the AMM-side push happens regardless), but a 30-block TWAP smooths the manipulated price across the hold window, so the oracle never reads low enough to liquidate. This is what TWAP oracles are for.

  7. Click ↻ MAINNET

    Replaces the default pool TVLs with an April 2026 mainnet snapshot — $215M USDC/WETH, $42M WBTC/WETH, $31M WBTC/USDC, $102M USDC/USDT. Real pools also concentrate more aggressively in the tight band, so swap impact per dollar drops. The simulator resets and you can compare MEV economics on real-pool depths.

  8. Pan and zoom the price chart

    The chart now does candlesticks. +/− to zoom in/out, ‹/› to pan, ⤢ to reset. Mouse wheel zooms; click-and-drag pans freely. Toggle between LINE and CANDLES; pick bar size 1, 5, 15, or 60 blocks. At mainnet 12s blocks, "5" gives you 1-minute candles.

  9. Click any agent card

    Opens a modal with the agent's decision rules, edge, and the academic reference for the strategy. Worth doing for FD2 (momentum) and FD3 (meanrev) — they were added in v2 and have non-trivial trigger conditions.

  10. Download the swap log or event log

    ⬇ SWAPS exports every executed trade with block, sim_time, pool, side, size, price, agent, tag. ⬇ MEV LOG exports the event stream — sandwich landings, JIT mints, oracle pushes, liquidations, block closes, builder switches.

The simulator is one HTML file with one inline script. There are no external dependencies. Everything from V3 swap math to candle aggregation is implemented inline.

I. Concentrated liquidity math

Each pool maintains sqrtP (the square-root of price, in token1/token0 convention) and a list of liquidity positions, each with bounds (sqrtPa, sqrtPb) and an L value. Active liquidity at any point is the sum of L over positions whose range contains the current sqrtP.

Swap step — selling token0 (sell0)
sqrtP_new = (L · sqrtP) / (L + Δx · sqrtP)
Δy = L · (sqrtP − sqrtP_new)
Swap step — selling token1 (sell1)
sqrtP_new = sqrtP + Δy / L
Δx = L · (1/sqrtP − 1/sqrtP_new)

When a swap would push price across a tick boundary, the simulator caps the step at the boundary, applies it, updates active L, and recurses — up to 32 hops per swap. This is the algorithm Uniswap V3 uses, in floating-point rather than Q64.96 fixed-point.

Display price vs internal price

V3's internal convention is price = token1/token0. For USDC/WETH that's WETH/USDC ≈ 1/3400, but the human-readable price is USDC/WETH = 3400. The simulator stores the internal V3 price in pool.sqrtP and exposes a displayPrice(pool) helper that flips for inverted pools. Swap math, fee accounting, and tick arithmetic use the internal price; the UI and USD conversion layer use the display side. Getting this wrong was the main bug discussed in the Bug Notes tab.

II. Mempool and block closure

Time advances one sim-second at a time. Every tick, agents may submit transactions to the mempool array, and searchers run their detection routines. Once simTime − lastBlockTime ≥ BLOCK_TIME (12s on mainnet, 1s on Unichain rollup), closeBlock() runs the builder auction.

FIG. 02Block closure with builder auction. Each builder constructs a candidate block; proposer picks highest value.

Sandwich bundles are kept atomic — a builder that includes a sandwich front always includes the matching victim and back-run as a contiguous triple. Builders that don't see the victim (because it's protected) drop the sandwich attempt entirely.

III. Searchers, agents, timing

Each sim-second the loop runs searcherStep(), retailStep(), and fundStep(). Searchers see only public mempool entries — anything marked tx.private = true (set when MEV-protected mode is active) is invisible to them.

Agent firing rates are modulated by a diurnal flow multiplier derived from empirical hourly DEX-volume data. Retail trade intervals scale inversely with the multiplier; fund firing rate scales directly. The schedule is bimodal — peaks at 13:00–17:00 UTC (US/EU overlap) and 01:00–05:00 UTC (Asia morning), trough at 06:00–10:00 UTC.

v2 fix

Fund decision rules use sim-seconds for lookback and cooldown windows, not blocks. Earlier versions used block counts which produced unintended behavior in rollup mode (1s blocks made momentum cooldowns 12× shorter, causing stairstep cascades). All time windows are now block-time-independent.

IV. Forensics and accounting

Every block, the simulator updates a forensics object with totals (swaps, volume, fees), MEV-specific counters (sandwich attempts, JIT mints, toxic backruns, oracle pushes, liquidations), and the cross-pool dislocation in bps. The forensics panel renders a mode-specific view plus two universal sections (Builder Competition and LP Aggregate · LVR) that always appear once the sim is running.

Per-agent capital and P&L are tracked in agentCapital and agentPnl. For LP positions, P&L decomposes into fees, IL (vs HODL), LVR (vs continuously-rebalanced 50/50 portfolio), and net-vs-rebalancing.

Eight agent types populate the simulator. The MEV searchers are off by default and activate only when the matching mode is selected.

The lending pool is the simulator's downstream protocol. Without it, oracle attacks have nowhere to land — the AMM round-trip is intentional loss for the attacker. With it, oracle manipulation becomes the sim's only consistently-profitable MEV form.

The setup

Eight borrowers post WETH as collateral and borrow USDC. They span the LTV spectrum from safe (50%) to edge (81%). The lending pool reads its WETH oracle from the USDC/WETH AMM. Every block, a liquidator scans positions and triggers liquidations on any account with health factor below 1.0.

Health factor and liquidation

Health factor
HF = (collateral_USD × liquidation_threshold) / debt_USD
liquidation_threshold = 0.825 (Aave V2 WETH parameter)

If HF drops below 1.0, the liquidator can repay up to 50% of the debt (the close factor) and seize collateral worth that amount plus an 8% bonus. The liquidator's profit is the bonus, minus their own slippage to convert seized WETH back to USDC. We approximate net profit as 85% of the gross bonus.

Spot vs TWAP oracle

The toggle is the lending oracle mode in the strategy bar. Two settings:

ModeWhat it readsVulnerability
spot Current pool price (one-block snapshot) Single large swap can move it 4–6%, triggering immediate liquidations
twap Geometric mean of last 30 blocks Attacker must hold the manipulated price for the whole window
TWAP oracle (window N)
oracle_price = exp( (1/N) × Σᵢ log(price_i) ) for i in last N blocks

Why the oracle attack works (and doesn't, with TWAP)

ORC1 sells $50M of WETH on USDC/WETH. With $120M default TVL and ~70% concentrated in the tight band, the active depth at price is ~$42M. A $50M swap pushes price about 5%. Most borrowers in the LTV-distribution table above have liquidation thresholds inside that 5% band — so HF crosses 1.0 for 3–8 of them.

With spot oracle: the manipulated price is what the lending pool sees. ORC1 liquidates the unhealthy borrowers at the depressed price, collects the 8% bonus on $200k–$2M of seized collateral. Net profit ≈ $50–150k per attack.

With TWAP-30: the oracle is the geometric mean of the last 30 blocks. Even when the spot price is depressed 5%, the TWAP barely moves because 29 of the 30 data points are unaffected. To corrupt a 30-block TWAP, ORC1 would need to hold the manipulated price for 30+ blocks, which means $50M × 30 blocks of capital lockup and 30 blocks of accumulated slippage. The math doesn't close. ORC1's profit drops by about 80%.

Important caveat

In TWAP mode, you'll still see some liquidations during a price push — those are organic, caused by the natural variance in WETH price during the warm-up period. But ORC1 only collects profit when its episode is active (the 8-block hold). After the episode unwinds, any remaining liquidations go to a generic liquidator bot, and ORC1 isn't credited. This is empirically correct: TWAP doesn't prevent liquidations from happening; it prevents the attacker from being the one who profits.

Historical context

Real exploits in this category include Mango Markets (Oct 2022, $114M), Cream Finance (Oct 2021, $130M), and Inverse Finance (April 2022, $15M). All used variants of the pattern modeled here: borrow flashloans, push an AMM price, exploit a downstream protocol that read that price as oracle, unwind. Most current lending protocols have moved to TWAP or multi-source (Chainlink) oracles in response.

Two universal forensic sections appear once the sim is running: Block Builder Competition and LP Aggregate · LVR. Both apply to every mode.

Block builder competition

Real Ethereum (post-MEV-Boost) has many block-builders. Each takes the available transactions and constructs a candidate block. Each block has a value — the sum of priority fees plus searcher kickbacks. The proposer picks the highest-value block.

The simulator runs four builders every block:

BuilderMempool visibilitySandwich policyKickback
flashbots-classic Public only Allowed 0 bps
protect-builder Public + protected Refuses on private victims 0 bps
searcher-aligned Public only Allowed, kickback-incentivized 100 bps on bundles
neutral Public only Allowed but random ordering 0 bps

In normal mode, Flashbots-Classic wins most blocks because its straightforward gas-priority sort produces consistent value. Searcher-Aligned wins the blocks with large sandwich bundles (the kickback puts it ahead). Protect-Builder wins zero blocks unless protected mode is active — without private orderflow it has nothing the other builders can't see.

In protected mode, the picture flips: Protect-Builder wins every block because it's the only one that can include the private retail/fund txs. The other builders' candidate blocks are nearly empty.

LP aggregate · LVR

The forensics panel decomposes LP P&L into four components:

ComponentDefinitionSign convention
currentUsd Current USD value of the LP position at fair price Positive
feesUsd Fees earned in the pool (cumulative) Positive when accumulated
ilUsd currentUsd − HODL value of original token mix Negative whenever price moves vs entry
lvrUsd HODL value − rebalancing portfolio value Negative when rebalancer would have done better
netVsRebalUsd (LP value + fees) − rebalancer value The single most informative number

HODL is the original token mix held forever. Rebalancing is a continuously-rebalanced 50/50 portfolio at fair price — the strategy a CEX-trading market-maker would run. LVR is the gap between these two: how much an LVR-aware rebalancer would have done better than just sitting in the original mix.

The most informative single number is netVsRebal — it answers "should I have been an LP, or rebalanced on a CEX?" Negative means the rebalancer wins. Positive means the LP captured enough fees to offset both IL and LVR.

What changes the LVR number

  • Volatility — LVR scales with σ². A quiet trading session has near-zero LVR; a volatile one can blow past fee revenue.
  • Toxic mode — Toxic backrunners specifically extract LVR. Running in toxic mode for +24h shows LVR accumulating faster than fees offset it.
  • Oracle attacks — During an attack, prices on USDC/WETH move 5%+ then snap back. LPs eat the round-trip IL.
  • Diurnal effects — LVR is worse for LPs in the 06:00–10:00 UTC trough hours, when CEX volumes are higher than DEX volumes and arbs widen the gap.

The "fair price" estimator

Computing LVR requires a CEX-equivalent fair price. The simulator approximates it as the average of two estimators:

Fair WETH price
e1 = displayPrice(USDC_WETH)
e2 = displayPrice(WBTC_USDC) / displayPrice(WBTC_WETH) // synthetic via WBTC
fair_weth = (e1 + e2) / 2

Both estimators converge fast under the cross-pool stat-arb agent's pressure. In practice they're within a few bps of each other, so the average is a stable proxy for the external CEX price.

Five bugs were diagnosed during the simulator's development. Each fix exposed a deeper assumption that turned out to be wrong. They're documented here in the order they were found because they're useful examples of how subtle the interactions between AMM mechanics, agent timing, and accounting can be.

Bug 1 — Sandwich bundles never resolved

Symptom

Forensics showed 35 sandwich attempts, 0 profitable, $0 P&L. The searchers were firing, the events were logging, but no profit was ever recorded.

Bundle assembly worked by iterating over pending mempool txs and matching each to a bundle by pairedVictimId. The bug: the victim itself doesn't carry pairedVictimId — only the front and back txs do. The victim is what the paired-id points to. The matcher iterated past every victim, leaving b.victim always null, so the profit-computation loop's guard always tripped.

Before — broken
pending.forEach(t => {
  if (t.pairedVictimId !== undefined) { // ⚠ skips victim
    for (const [fid, b] of bundleByFrontId) {
      if (b.front.pairedVictimId === t.id) b.victim = t;
    }
  }
});
After — fixed
pending.forEach(t => {
  for (const [fid, b] of bundleByFrontId) { // scan all
    if (b.front.pairedVictimId === t.id) b.victim = t;
    if (t.type === 'sandBack' && t.pairedFrontId === fid) b.back = t;
  }
});

After this fix, attempts started resolving. But every single one was a loss, every time. The search continued.

Bug 2 — Inverted price convention

Symptom

Every sandwich attempt on USDC/WETH or WBTC/WETH lost money in a specific pattern: the front-run output and the back-run input had wildly inconsistent USD values.

Uniswap V3's internal convention is price = sqrtP² = token1 / token0. The simulator's swap math used this correctly. But the POOLS config stored initialPrice values in the human-readable convention — "USDC per WETH = 3,400" rather than "WETH per USDC = 1/3,400". For two of the four pools (USDC/WETH and WBTC/WETH) the values were inverted.

The swap math was internally consistent but operating in the wrong direction for those pools. Selling token0 (USDC) pushed the displayed price down when it should have pushed it up. For the sandwich agent, this meant the front-run pushed price the opposite direction of intent, the victim pushed it further opposite, and the back-run sold into a pool whose price had moved against the searcher every step — guaranteed loss, every time.

The fix was to restructure all four pools to store internal V3 prices uniformly, with a separate displayPrice(pool) helper that handles the inversion for UI and USD conversion:

POOLS config — uniform convention
USDC_WETH: { token0: 'USDC', token1: 'WETH', initialPrice: 1 / REF.WETH, invertDisplay: true }
WBTC_WETH: { token0: 'WETH', token1: 'WBTC', initialPrice: REF.WETH / REF.WBTC, invertDisplay: true }
WBTC_USDC: { token0: 'USDC', token1: 'WBTC', initialPrice: 1 / REF.WBTC, invertDisplay: true }
USDC_USDT: { token0: 'USDC', token1: 'USDT', initialPrice: 1.0, invertDisplay: false }

All swap math, fee accounting, and tick arithmetic operate on the canonical internal price. The chart, top bar, and tape pass values through displayPrice() before showing them.

Bug 3 — Back-run input was the wrong amount

Symptom

Sandwiches now profitable in principle, but the back-run was leaving small amounts on the table — the searcher's net token position was off by a few percent.

At submission time, the back-run's input amount was set to a simulated expected output of the front-run, computed against pool state before the front actually executed. By the time the back ran, the front had already moved the pool and its actual output differed slightly. The back was trying to swap exactly what was predicted, but the searcher held the realised amount.

Real sandwich bundles are atomic — the back's input is whatever the front returned, not a pre-simulated estimate. The fix was a small patch in executeTx for sandBack txs only — read the front's actual amountOut and use that as the back's amountIn at execution time.

Bug 4 — Naive sizing triggered victim reverts

Symptom

With prices and accounting fixed, sandwiches were profitable on individual bundles but the success rate was poor. Many attempts had the front execute, then the victim revert (slippage exceeded), leaving the searcher's front position stuck with no exit.

The original sandwich sizing aimed to extract maximum impact, ignoring the constraint that the victim's slippage tolerance is finite. If the front pushed price too far, the combined front+victim impact would exceed the victim's slippageBps, the victim's swap would revert, and the searcher would be left with a position that the back-run had to unwind into a worsened pool — almost always at a loss.

The fix: size the front so that combined front+victim impact stays within the victim's slip budget, and gate on expected dollar profit before submission.

Sandwich sizing — current implementation
headroom_bps = victim_slip_bps − victim_impact_bps
if headroom_bps < 5: skip
size_fraction = clamp(0.7 × headroom_bps / victim_impact_bps, 0.2, 2.0)
front_usd = min(victim_size × size_fraction, searcher_capital × 0.7)

gross_extract = victim_size × front_impact_bps / 10000
fee_cost = 2 × front_usd × pool_fee_bps / 10000
gas_cost = $50
expected_profit = gross_extract − fee_cost − gas_cost

if expected_profit < $50: skip
if front_impact_bps + victim_impact_bps > victim_slip_bps − 2: skip

After this iteration, the simulator reports a roughly 60% sandwich success rate on whale victims in the 5bp pool — close to historical Flashbots data on mainnet sandwich landings.

Bug 5 — Systematic upward price bias in sandwich mode

Symptom (user-reported)

"When sandwich attacks are present there seems to be a bias towards a rising price in the chart. Is this simply due to the inter-agent dynamics?"

Investigated by running 5 trials × 1,000 blocks in none mode (no MEV) and measuring price drift:

ModeWETH drift (mean of 5)WBTC driftSandwich attempts
none (before fix)+1.45%+1.54%0
sandwich (before fix)+0.19%+0.96%~10/run
none (after fix)+0.01%+0.01%0
sandwich (after fix)−0.02%−0.01%~10/run

The bias was real but had nothing to do with sandwich attacks. The fund-bias selector was Math.random() < 0.5 ? 'long-eth' : 'long-btc' — every fund was perpetually long-only, never short. Three funds buying continuously, with only symmetric retail flow as counter-pressure, produced the drift. The fix expanded the bias pool to four directions distributed across the funds, plus per-fund bias flipping every 5–15 blocks.

Sandwich attacks themselves are theoretically price-neutral. The front and back are equal-and-opposite swaps that cancel in expectation; the only price residue the bundle leaves is the victim's own impact, which would have happened anyway.

Bug 6 — Stairstep pattern in rollup mode (v2)

Symptom (user-reported)

"What happens with Unichain rollup-boost? The trend appears to be a step-wise function upwards only."

The reactive funds added in v2 measured their lookback windows in blocks rather than sim-seconds. In mainnet mode (12s blocks), lookbackBlocks: 5 meant the momentum fund evaluated price moves over 60 sim-seconds. In rollup mode (1s blocks), the same value meant 5 sim-seconds — a 12× shorter window.

This created two cascading problems in rollup mode. First, the 50bps trigger threshold was rarely tripped by organic flow — but when it was, the fund fired a $300k–$1M directional buy that moved price ~5–10bps, which kept the trailing 5-second return above 50bps. Second, the cooldown blockNumber + 2 was a 24-second pause on mainnet but only 2 seconds on rollup. As soon as cooldown expired, the trailing window still showed > 50bps and momentum fired again, in the same direction. Repeat.

The result was a stairstep: a single triggering tx kicked off 5–10 follow-on momentum buys before the trailing window fell back below threshold. It looked like an upward bias because momentum is asymmetric — it always trades with the recent direction, so whichever direction the first trigger picked dominated.

The fix: all fund decision rules now use sim-seconds for lookback and cooldown windows. Same parameters describe the same temporal behavior regardless of block time. After the fix, drift is centered at zero in both modes (mainnet and rollup), with similar variance.

Coupled lending pool

Eight WETH-collateralized borrowers, LTVs from 50% to 81%. Lending oracle reads from USDC/WETH AMM, configurable as spot or twap (30-block geometric mean). Liquidator competes for liquidations at an 8% bonus. Oracle attacks now have a downstream profit path: ORC1 sells $50M of WETH, pushes price ~5%, holds 8 blocks, liquidates 3–8 borrowers at the depressed price. With spot oracle, ORC1 nets $50–150k per attack. With TWAP-30, profit drops by ~80%.

Five fund subtypes (replaced flippy-only)

FD1 flippy (baseline), FD2 momentum, FD3 meanrev, FD4 info (OU signal), FD5 whale. Together they generate flow with realistic temporal autocorrelation: bursts, follow-through, occasional whale events. All decision rules use sim-seconds for timing windows, so behavior is consistent across mainnet (12s blocks) and rollup (1s blocks).

Multi-builder competition

Four builders compete every block: Flashbots-Classic, Protect-Builder, Searcher-Aligned, Neutral. Each constructs a candidate block from txs they can see and computes its block value. Proposer picks the highest. Forensics shows per-builder win count and total value extracted.

LVR accounting

Every LP position now exposes hodlUsd, rebalUsd, ilUsd, lvrUsd, and netVsRebalUsd. The forensics panel has a new universal "LP Aggregate · LVR" section showing the full decomposition. Fair-price proxy uses the average of two cross-pool estimators.
